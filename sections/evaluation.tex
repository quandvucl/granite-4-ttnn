\section{Evaluation}

\subsection{Experimental Setup}

\subsubsection{Hardware}

The CPU and Wormhole devices share the same host machine (AMD EPYC 9354P, 32 cores at 3.8\,GHz with 2-way hyperthreading, 566\,GB DDR5 RAM). The A100 is located in a separate server (NVIDIA A100 PCIe 80\,GB~\citep{nvidia2020a100}, 1{,}935\,GB/s HBM2e bandwidth, 312\,TFLOPS BF16; host: Intel Xeon Icelake, 14 cores, 117\,GB RAM) on the same network.

\subsubsection{Software}

All Python code runs under Python 3.10.12. The Wormhole backend uses TTNN~0.67.0 (tt-metalium). The HuggingFace baselines use \texttt{transformers}~4.57.1 with PyTorch~2.3. The A100 node runs NVIDIA driver 595.45.04 with CUDA~13.2.

\subsubsection{Configurations}

Four primary configurations are used as baselines:

\begin{itemize}
\item \textbf{TT-tiny}: Granite-4.0-h-tiny on 1$\times$4 Wormhole submesh (4 chips, fabric enabled). All weights \texttt{bfloat16}. Decode trace enabled.
\item \textbf{TT-small}: Granite-4.0-h-small on 8$\times$1 Wormhole submesh (8 chips, fabric enabled). MoE weights in \texttt{bfloat8\_b}, all others \texttt{bfloat16}. Decode trace enabled.
\item \textbf{CUDA-tiny / CUDA-small}: HuggingFace reference on the NVIDIA A100 80\,GB GPU, \texttt{bfloat16}, without \texttt{torch.compile}. A compiled variant (\texttt{torch.compile} with the \texttt{inductor} backend) was also run for comparison (see Section~\ref{sec:discussion-compile}).
\item \textbf{CPU-tiny / CPU-small}: Same HuggingFace reference on the host machine CPU, \texttt{float32}, without \texttt{torch.compile}. A compiled variant was also run for comparison.
\end{itemize}

In total, 24 benchmark runs were performed: 10 on Tenstorrent with both kernels enabled (2 models $\times$ 5 chunk sizes: 192, 256, 320, 384, 512), 6 kernel ablation runs (2 models $\times$ 3 kernel configurations: no kernels, conv1d only, SSM only), 4 on CUDA (2 models $\times$ with/without \texttt{torch.compile}), and 4 on CPU (same). The default chunk size of 256 and the uncompiled CUDA and CPU paths are used as the primary baselines throughout the paper.

Five prompts of increasing length are used: 5, 8, 25, 96, and 176 tokens. Each backend generates 20 tokens per prompt. Let $t_i$ be the time (in seconds) from submitting the $i$-th input token to receiving the corresponding logits (i.e., the time to produce one output token). Decode throughput is
\begin{equation}
  \text{tok/s} = \frac{1}{\frac{1}{19}\sum_{i=2}^{20} t_i},
  \label{eq:throughput}
\end{equation}
where step 1 is excluded because it is slightly slower after a cache reset. At each step, a repetition penalty $p{=}1.3$ is applied to the logit $z_j$ of every token $j$ that has already appeared in the output:
\begin{equation}
  z_j \leftarrow \begin{cases} z_j / p & \text{if } z_j > 0 \\ z_j \times p & \text{if } z_j \leq 0. \end{cases}
  \label{eq:rep-penalty}
\end{equation}
Dividing a positive logit by $p{>}1$ lowers it, and multiplying a negative logit by $p$ makes it more negative. Both operations reduce the probability of repeating already-seen tokens.

\subsection{Results}

\subsubsection{Kernel ablation}
\label{sec:eval-kernel-ablation}

A \emph{kernel ablation} measures the contribution of each optimisation in isolation by disabling one component at a time and observing the effect on throughput. Table~\ref{tab:kernel-ablation} shows decode throughput for each combination of the two fused kernels (\texttt{ssm\_update} and \texttt{conv1d\_decode}, described in Section~\ref{sec:optimisation}), with trace always enabled.

\begin{table}[h]

\toprule
Fused kernel configuration & tiny (tok/s) & small (tok/s) \\
\midrule
No fused kernels              & 10.52 & 5.75 \\
\texttt{conv1d\_decode} only  & 10.60 & 5.82 \\

Both fused kernels contribute independently to decode throughput. For the tiny model, \texttt{conv1d\_decode} adds ${\approx}0.08$ tok/s and \texttt{ssm\_update} adds ${\approx}0.04$ tok/s over the no-kernel baseline; combined they add ${\approx}0.15$ tok/s (${\approx}1.4\%$). For the small model, \texttt{conv1d\_decode} adds ${\approx}0.07$ tok/s. \texttt{ssm\_update} alone provides no measurable gain but contributes an additional ${\approx}0.04$ tok/s when combined with \texttt{conv1d\_decode}. The absolute gains are modest because generating one token at a time means most of the time is spent reading model weights from memory, not doing computation — so reducing the number of operations per Mamba2 step only saves a small fraction of the total step time.

\subsubsection{Output quality}
\label{sec:eval-quality}

Both models on Wormhole with trace enabled produce coherent, on-topic responses across all five prompts. All five TTNN chunk-size variants produce token-for-token identical outputs, confirming that chunk size does not affect generation quality. Six distinct agreement patterns are observed:

\begin{itemize}
  \item \textbf{WH, CPU, CPU+compile, A100, A100+compile all identical.} Example — tiny, \textit{``The largest planet in our solar system is''}: all backends: \textit{``Jupiter. It has a diameter of about 88,846 miles (142,984 kilometers), which makes\ldots''}

  \item \textbf{WH close to CPU and A100 but differs at the tail.} Agreement through most tokens, divergence on the last few words. Example — tiny, \textit{``The capital of France is''}: WH: \textit{``\ldots skyline and one that many people\ldots''}; CPU / A100: \textit{``\ldots skyline and one among many tourist\ldots''}

  \item \textbf{CPU and CPU+compile always identical.} \texttt{torch.compile} does not change output on CPU. Example — tiny, long\_128: CPU and CPU+compile both: \textit{``\ldots or other techniques for improved efficiency. However, despite their impressive capabilities, LLMs still face\ldots''}

  \item \textbf{A100 and A100+compile can differ.} Triton autotuning changes floating-point operation order. Example — tiny, long\_128: A100: \textit{``\ldots like LSTMs or GATs for improved performance. The training process involves\ldots''}; A100+compile: \textit{``\ldots like LSTMs or GATs (Graph Attention Networks) for improved performance. However, despite\ldots''}

  \item \textbf{CPU and A100 differ on longer prompts.} float32 (CPU) vs.\ bfloat16 (A100) accumulation diverges over many tokens. Example — tiny, long\_128: CPU: \textit{``\ldots or other techniques for improved efficiency\ldots''}; A100: \textit{``\ldots like LSTMs or GATs for improved performance\ldots''}

  \item \textbf{WH differs from both CPU and A100 on longer prompts.} WH uses bfloat16 on different hardware with a different tokenizer. Example — tiny, long\_128: WH: \textit{``\ldots like LSTMs or RNNs for improved performance\ldots''}; CPU: \textit{``\ldots or other techniques for improved efficiency\ldots''}; A100: \textit{``\ldots like LSTMs or GATs for improved performance\ldots''}
\end{itemize}

\subsection{Discussion}

\textbf{Tiny model: Wormhole exceeds A100.}
The tiny model on 4 Wormhole chips (10.65--10.69 tok/s) is ${\approx}18\%$ faster than the A100 (8.5--9.0 tok/s). Decode trace recording (Section~\ref{sec:challenges}) replaces the per-token command overhead with a single replay call, which is the key reason Wormhole wins at this scale. The A100 has years of software optimisation behind it, so outperforming it on a relatively new and less mature hardware platform is a strong result.

\textbf{Small model: Wormhole below A100.}
The small model on 8 chips (5.84--5.89 tok/s) is ${\approx}20\%$ slower than the A100 (7.1--8.2 tok/s). The bottleneck is reading weights from memory: at this model size, each token generation must load a large amount of data across 8 chips, and the 8$\times$1 mesh has less total memory bandwidth than the A100's HBM2e. Trace is enabled but the memory cost outweighs the command overhead savings.

\textbf{CPU baselines.}
Both CPU results (2.5--2.6 tok/s tiny, 0.65--0.66 tok/s small) are far below Wormhole and A100. Wormhole is ${\approx}4\times$ faster than CPU for tiny and ${\approx}9\times$ for small. \texttt{torch.compile} gives no meaningful improvement on CPU for this model family (Section~\ref{sec:discussion-compile}).

\textbf{Constant decode rate on Wormhole.}
Wormhole throughput does not change across prompt lengths (10.65--10.69 tok/s for tiny, 5.84--5.89 tok/s for small) because the trace replays the same fixed sequence of operations regardless of how long the input was. The A100 without \texttt{torch.compile} dips slightly at medium prompt lengths (med\_32, long\_128), likely because its GPU kernels are less efficient at those particular input sizes.

\textbf{Fused kernel gains at larger batch sizes.}
All benchmarks in this paper use batch size 1, where each token generation step reads the full model weights from memory but does very little arithmetic. When only one token is generated at a time, the time saved by fusing operations is small compared to the total weight-reading cost, which is why the kernel gains are only ${\approx}1$--2\%. At larger batch sizes, the same weights are shared across multiple requests in a single step, so reading weights becomes less of a bottleneck and the arithmetic savings from fused kernels matter more. The current implementation does not support batched decode, but extending the fused kernels to batch size $>1$ is a natural next step and would likely yield more significant gains.

\textbf{\texttt{torch.compile} on CPU and CUDA.}
\label{sec:discussion-compile}
\texttt{torch.compile} does not improve throughput for either backend. On CPU, compiled decode (2.45--2.46 tok/s tiny, 0.64--0.65 tok/s small) is marginally slower than uncompiled, with similar prefill time after warmup. On CUDA, compiled decode (5.27--6.15 tok/s tiny, 4.83--6.83 tok/s small) is substantially slower than uncompiled (8.5--9.0 tok/s tiny, 7.1--8.2 tok/s small). The main reason is that the Mamba2 recurrent state prevents CUDA graph capture, which is the primary mechanism by which \texttt{torch.compile} speeds up GPU inference; without it, the compilation overhead outweighs any gains. The notably lower result for small at short\_8 (4.83 tok/s) is because \texttt{torch.compile} runs additional setup work the first time it sees a new input size, which slows down that prompt's benchmark. The A100 rows in Tables~\ref{tab:tiny-decode} and~\ref{tab:small-decode} therefore use the uncompiled path.
