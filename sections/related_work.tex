\section{Related Work}

Previous work has explored LLM deployment on GPUs, TPUs, and custom accelerators. Systems such as TensorRT and XLA aim to optimize execution by compiling models to hardware-specific representations. Mamba-series models~\citep{gu2023mamba,dao2024transformers} have been shown to match transformer quality at reduced inference cost on GPUs, but their recurrent decode is harder to run efficiently on Tenstorrent hardware. Each decode step must update a hidden state, read from it, and produce an output — three dependent operations that cannot be merged without a custom kernel. In TTNN, each operation is a separate command sent from the host CPU to the device, and at batch size 1 the data processed is small enough that sending the command takes longer than the computation itself. A transformer step spends most of its time in large matrix multiplications (attention and feed-forward), so the per-command cost is negligible compared to the actual computation. Expert-parallel inference for sparse MoE models has been studied for GPU clusters~\citep{lepikhin2021gshard}, but the interaction between collective operations and trace replay has not been characterised for Wormhole-class hardware.

Running large language models on non-GPU hardware consistently requires more than simply moving the existing code to a new machine. Each accelerator has its own rules for how computation must be organised, and code written for GPUs typically cannot run efficiently without being reworked to match those rules.

He~et~al.~\citep{he2025waferllm} show this for a processor built on an entire silicon wafer. Unlike a GPU, which processes operations one after another in a flexible order, this chip requires the full sequence of operations to be laid out in advance so that data flows directly from one processing unit to the next without waiting. Getting a model to run efficiently on such hardware means reorganising its operations into a form the chip can execute in a single continuous pass.

SambaNova~\citep{sambanova2025dataflow} and Groq~\citep{groq2025lpu} present related but distinct constraints. SambaNova's chip configures a fixed data routing layout at compile time: the compiler decides in advance which processing units handle which operations and how data flows between them, and this layout cannot change during execution. Groq goes further, assigning every operation a fixed position in the execution timeline before the program runs, so the entire sequence of computations is determined in advance with no runtime variation. In both cases, parts of a model that change their behaviour depending on the input --- for example, taking different paths through the computation depending on what the previous step produced --- must be rewritten as a single fixed sequence of steps that the hardware can plan in advance.

This project encounters the same problem on Tenstorrent Wormhole. As described in Section~\ref{sec:challenges}, two parts of the model required manual rewriting that would have worked automatically on a GPU: the order in which results are shared between chips had to be changed to fit within the constraints of the trace mechanism, and a custom operation had to be written for the recurrent memory update because the hardware's software library did not support it directly.
